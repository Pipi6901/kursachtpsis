# Тестирование и проверка работоспособности

Документ описывает стратегию и результаты проверки программного средства: автоматические тесты всех трёх узлов, валидацию
интеллектуального компонента, проверки на реальной СУБД PostgreSQL и проверку того, что данные существующей системы не затронуты.

## 1. Стратегия и план

| Уровень | Что проверяется | Средства |
|---|---|---|
| Модульные тесты | преобразования данных, модели, шифрование, парсеры, форматирование, построение графиков | pytest, JUnit 5, Jasmine |
| Интеграционные тесты сервера | полный контекст Spring: безопасность по ролям, REST, транзакции, БД, шлюз ИИ на реальном HTTP-сервере-имитации | JUnit 5, MockMvc, H2 (основная БД не затрагивается) |
| Контрактные тесты | формат обмена «сервер ↔ ML» (snake_case, коды ошибок, ключ доступа) в обе стороны | FastAPI TestClient; шлюз против имитации ML на настоящем HTTP-порту |
| Компонентные тесты клиента | панель прогноза и навигация с подставным сервисом, охранник маршрутов, HTTP-клиент | Karma + Jasmine, Chrome Headless |
| Валидация интеллектуального компонента | точность, интервалы, восстановление вклада каналов, польза оптимизации — на данных с **известной «истиной»** | pytest, `ml-service/tools/validation_report.py` |
| Комплексные проверки | вся цепочка на настоящей PostgreSQL и настоящих процессах: вход, прогноз, сбой и восстановление, TLS, копии, самовосстановление | вручную (раздел 4) |
| Проверки интерфейса | сценарии работы в браузере, роли, деградация | headless-Chromium (Playwright) |

Критерии успеха: все автоматические тесты проходят; ошибка прогноза на проверочных неделях ниже ориентиров (сезонной наивной модели и модели
Хольта–Уинтерса); вклад каналов восстанавливается с отклонением нескольких процентных пунктов; рекомендация оптимизатора улучшает истинный
эффект; при сбое любого узла система остаётся работоспособной.

Что покрывают наборы (выборочно):

* **ML-сервис**: перенос эффекта (adstock) и насыщение; сезонные признаки и праздники; маркетинговый микс (неотрицательные коэффициенты, точное

  бустинг (монотонность, детерминированность); границы окон проверки и интервалы; оптимизатор (весь бюджет расходуется, равенство предельных

* **Сервер**: доступ по JWT и ролям (гость → 403, менеджер не обучает и не удаляет, неверный токен → 401); создание данных и демо-загрузка;

  согласованный набор данных; прогноз согласован с вкладами каналов; сценарии меняют затраты, уходящие в сервис; недопустимые значения
  отклоняются; кэш; **деградация при отказе сервиса и размыкание предохранителя**; оптимизация; жизненный цикл кампаний и каналов;
  ввод, импорт и удаление продаж; устаревание модели при новых данных и контроль дрейфа; откат версии; потеря модели в реестре ML и
  недоступность сервиса (не путаются); производные значения вычисляются, а не хранятся (3НФ).
* **Клиент**: форматы чисел и дат на русском; ряды, подписи и скрытые служебные ряды графиков; цвета каналов закреплены за каналом;
  HTTP-запросы и отключение общего индикатора загрузки; охранник пропускает только администратора и менеджера; панель: параметры запроса,
  объединение быстрых изменений в один запрос (debounce), упрощённый режим, ошибки сервера, оптимизация, применение рекомендации,
  устойчивость к бесконечному циклу проверки изменений.

## 3. Тестирование и валидация интеллектуального компонента

Реальных продаж в проекте нет, поэтому интеллектуальный компонент проверяется на **синтетических данных с известными параметрами**
(генератор `ml-service/tools/synthetic.py`: тренд, годовая сезонность, праздники, шесть каналов с известными переносом эффекта и насыщением,
шум 5,5 %). Это позволяет проверить не только «насколько близок прогноз», но и «правильно ли восстановлен вклад каналов» — на реальных
данных истину узнать нельзя. Отчёт воспроизводится командой `python -m tools.validation_report docs/validation-report.md` из каталога `ml-service`
(полный текст — [ml-service/docs/validation-report.md](../ml-service/docs/validation-report.md)).

**Скользящая кросс-валидация (4 окна по 12 недель), выручка:**

| Алгоритм | Учитывает маркетинг | WAPE | Выигрыш к наивной |
|---|---|---|---|
| Сезонная наивная (ориентир) | нет | 9,11 % | 0 % |
| Хольта–Уинтерса | нет | 8,33 % | 8,5 % |
| **Маркетинговый микс (MMM)** — выбран | да | **6,03 %** | **33,8 %** |
| Градиентный бустинг | да | 7,23 % | 20,6 % |

**Проверка вне выборки** (обучение на 170 неделях, прогноз 26 недель): WAPE 5,51 %, смещение −0,17 %; фактическое покрытие
80 %-го интервала — **84,6 %** (интервал немного консервативен).

**Восстановление вклада каналов** (бронирования): общий вклад маркетинга — оценка 6625 против истинных 6653 (отклонение **0,4 %**);
доли отдельных каналов отклоняются от истинных на 0,6–3,3 п. п. (например, агрегаторы: 41,7 % против 44,6 %).

**Польза оптимизации** (12 недель, бюджет 20 040 $; эффект оценён по истинной функции отклика, которой модель не видела):

| Распределение | Эффект, бронирований | К плану |
|---|---|---|
| План менеджера | 437 | — |
| Равномерное по каналам | 447 | +2,3 % |
| **Рекомендация оптимизатора** | **501** | **+14,6 %** |

Дополнительно проверено: оптимизатор находит точное решение вогнутой задачи и выполняет условие оптимальности (равные предельные отдачи у
каналов внутри допустимых границ); ограничения долей соблюдаются; канал с постоянными затратами помечается предупреждением «оценка вклада
ненадёжна»; интервал расширяется за горизонтом проверки.

**Ограничение валидации.** Результаты получены на синтетике, построенной той же структурной моделью (тренд × сезонность + насыщаемые каналы), поэтому
они подтверждают корректность реализации и вычислительную работоспособность, но не гарантируют такой же точности на реальных данных
конкретной гостиницы. На реальных данных используйте блок «Проверка на неизвестных неделях» и «Контроль качества после обучения».

## 4. Комплексные проверки на реальной БД и процессах

Цепочка «браузер → сервер → PostgreSQL / ML-сервис» проверена на настоящих процессах: PostgreSQL 16, сервер (jar), ML-сервис (uvicorn),
клиент (`ng serve`), настоящий вход по JWT. Проверенные сценарии и результаты:

| Сценарий | Результат |
|---|---|
| Первый запуск на пустой БД и на БД с таблицами гостиницы | таблицы модуля созданы, демо-данные загружены (196 недель, 6 каналов, 240 кампаний), две модели обучены автоматически за ≈10 с после старта (WAPE 6,03 % и 5,15 %) |
| Запуск с `FORECAST_DEMODATA_ENABLED=false` | таблицы созданы пустыми, данные не загружаются |
| Вход администратором, менеджером, пользователем | менеджер и администратор получают прогноз; пользователь — 403 (в интерфейсе пункта меню нет) |
| Прогноз, сценарии, оптимизация | идентичные результаты для одинаковых входов; сценарий «без маркетинга» отправляет нулевые затраты (прогноз остаётся выше базы на эффект ранее оплаченной рекламы) |
| Остановка ML-сервиса | интерфейс показывает «Упрощённый режим», прогноз сохраняется, оптимизация блокируется; через 15 с после запуска сервиса работа полноценна |
| Перезапуск ML-сервиса | реестр читает зашифрованные модели с диска, прогноз совпадает до рубля (236 457 $ на 12 недель) |
| HTTPS между узлами (самоподписанный сертификат) | с хранилищем доверия прогноз идентичен прогнозу по HTTP; без хранилища соединение отклоняется, система работает в упрощённом режиме |
| Перенос БД на «другой компьютер» (восстановление копии в новую БД при пустом реестре ML) | сервер обнаружил отсутствие обеих моделей и обучил заново за ≈8 с, результат идентичен |
| Резервная копия: вся база и только таблицы модуля | файл зашифрован (открытого текста нет), неверная фраза отклоняется, восстановление в новую БД даёт те же числа строк во всех таблицах; восстановление в непустую БД отменяется целиком |
| Скрипт удаления и повторная установка модуля | таблицы удалены, при запуске созданы заново; структура совпадает с `docs/sql/forecast-schema.sql` (столбцы, типы, ограничения, ключи) |
| Интерфейс (headless-Chromium) | панель, ползунки сценария, график по неделям, оптимизация и «Применить как сценарий», кампании (создание/удаление), страница модели, роли, упрощённый режим; ошибок в консоли браузера нет |

Быстродействие (ориентировочно, одна машина, 196 недель, 6 каналов): прогноз с обращением к ML-сервису — медиана 51 мс (95-й процентиль 66 мс);
оптимизация — медиана 84 мс; обучение четырёх алгоритмов со скользящей проверкой — около 3,5 с на показатель.

## 5. Проверка, что существующие данные не изменены

Модуль только добавляет таблицы `mk_*` и `fc_*`. Проверка выполнена сравнением полных выгрузок таблиц гостиницы **до** первого запуска модуля
и **после** полного цикла (установка → автоматическое обучение → копирование → удаление таблиц модуля → повторная установка): схема и данные всех
восьми прежних таблиц (`comments`, `receipts`, `reservation`, `roles`, `room`, `stats`, `users`, `users_roles`) совпали побайтно.

Повторить на своей базе (до запуска модуля и после):

```bat
pg_dump -U postgres --no-owner --inserts -t comments -t receipts -t reservation -t roles -t room -t stats -t users -t users_roles hotel > before.sql
rem ... запуск и работа с модулем ...
pg_dump -U postgres --no-owner --inserts -t comments -t receipts -t reservation -t roles -t room -t stats -t users -t users_roles hotel > after.sql
fc before.sql after.sql
```

(Строки `\restrict …`/`\unrestrict …`, которые добавляют свежие версии `pg_dump` со случайным значением, при сравнении исключите.)

## 6. Проверки безопасности

| Что проверяется | Как |
|---|---|
| Доступ по ролям, неверный и просроченный токен | интеграционные тесты сервера (403 / 401, а не 500) |
| Ключ между узлами | тесты контракта: без ключа и с неверным — 401; шлюз сообщает «отклонил ключ», а не «недоступен» |
| Шифрование моделей | тесты реестра: файл на диске не содержит открытого текста; подмена байта и неверная фраза обнаруживаются |
| Шифрование резервных копий | 29 тестов скриптов: неверная фраза, изменённый байт, изменённый заголовок, усечение на границе блока и посреди блока, перестановка блоков, не-копия, неверная версия |
| TLS | тест: сертификат принимается клиентом по имени `localhost` и отвергается без доверия; проверка на реальных процессах (раздел 4) |
| Валидация входа | недопустимые горизонты, множители, даты, выходящие за границы значения — 400 с понятным сообщением; CSV с ошибками не применяется частично |
| Пароль в командной строке | пароль БД передаётся утилитам `pg_dump`/`psql` через окружение (тест: пароля нет среди аргументов процесса) |

## 7. Как запустить тесты

```bat
scripts\windows\run-tests.bat
```

или по узлам:

```bat
cd ml-service       && .venv\Scripts\python -m pytest
ml-service\.venv\Scripts\python -m pytest scripts\tests
cd backend          && mvnw.cmd test
cd frontend         && npm run test:ci
```

Для тестов сервера не нужны ни PostgreSQL, ни ML-сервис: используется встроенная H2 и имитация ML-сервиса на локальном порту. Тесты клиента требуют
установленного Google Chrome (в среде без экрана — переменная `CHROME_BIN`; запуск без песочницы уже настроен в `karma.conf.js`).

## 8. Результаты и оценка надёжности

| Показатель | Значение |
|---|---|
| Автоматических проверок | 189 (ML 60, скрипты 29, сервер 53, клиент 47), все проходят |
| Ошибка прогноза выручки (WAPE) на неизвестных неделях | 6,0 % (ориентир «как в прошлом году» — 9,1 %) |
| Покрытие интервала 80 % | 84,6 % |
| Отклонение общего вклада маркетинга от истинного | 0,4 % |
| Прирост эффекта по рекомендации оптимизатора | +14,6 % к плану менеджера |
| Поведение при отказе интеллектуального узла | прогноз доступен (упрощённый режим), возврат к полной работе автоматический |
| Данные существующей системы | не изменяются (проверено сравнением выгрузок) |

**Известные ограничения.** Точность оценивалась на синтетических данных (раздел 3). Для надёжной оценки каналов нужны данные, в которых затраты
каналов менялись независимо друг от друга. Канал «браузер — сервер» не шифруется в учебной конфигурации (см. [architecture.md](architecture.md#8-информационная-безопасность)).
Версии существующих частей (Angular 14, Spring Boot 3.3.5) не обновлялись — см. [compliance.md](compliance.md).
