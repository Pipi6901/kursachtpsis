# Интеллектуальный сервис прогнозирования продаж

Изолированный микросервис (Python 3.13, FastAPI), который обслуживает модуль «Прогноз продаж»
гостиничной системы. Он **не имеет доступа к основной базе данных**: серверная часть (Spring Boot)
сама готовит данные и передаёт их по REST. Браузер с сервисом не взаимодействует — только сервер,
по общему секрету `X-API-Key`.

## Что умеет

| Операция | Описание |
|---|---|
| `POST /api/v1/models/train` | Обучает 4 алгоритма на недельном ряде продаж и затратах по каналам, сравнивает их скользящей кросс-валидацией, выбирает «чемпиона», сохраняет модель в реестр |
| `POST /api/v1/models/{id}/forecast` | Прогноз на 1–52 недели по плану затрат: интервал, базовый уровень, вклад каждого канала |
| `POST /api/v1/models/{id}/optimize` | Оптимальное распределение заданного бюджета между каналами |
| `GET /api/v1/models`, `GET /api/v1/models/{id}` | Реестр моделей, качество, параметры каналов |
| `GET /health` | Проверка работоспособности (без ключа) |

Интерактивная документация: `http://localhost:8001/docs`.

## Алгоритмы

* **Сезонная наивная** и **Хольта–Уинтерса** — ориентиры, не учитывают маркетинг.
* **Маркетинговый микс (MMM)** — регрессия с ограничениями: тренд, годовая сезонность (ряды Фурье),
  праздники и по каждому каналу `β·(1 − exp(−adstock(x)/k))`. `adstock` — перенос эффекта рекламы на
  следующие недели, `1 − exp(−a/k)` — убывающая отдача, `β ≥ 0`. Гиперпараметры подбираются блочной
  кросс-валидацией только на обучающем окне.
* **Градиентный бустинг** — нелинейный претендент (монотонность по затратам, тренд вычитается отдельно).
* Чемпионом становится лучшая по WAPE модель, **учитывающая маркетинг**; бустинг заменяет MMM лишь при
  выигрыше более 5 % (иначе предпочитается интерпретируемая модель).
* Интервал прогноза строится по эмпирическим квантилям относительных ошибок кросс-валидации
  (за пределами горизонта валидации расширяется), вклад каналов — разложением MMM или методом исключения.
* Оптимизатор решает задачу распределения ресурса с вогнутой целью точно (равенство предельных отдач),
  не выходя за наблюдавшийся диапазон затрат ×1,5.

Результаты проверки на данных с известной «истиной» — в [docs/validation-report.md](docs/validation-report.md).

## Запуск (Windows 10/11 и новее, Python 3.12+ — рекомендуется 3.13)

```bat
cd ml-service
python -m venv .venv
.venv\Scripts\activate
pip install -r requirements.txt
set ML_API_KEY=ваш-секретный-ключ
set ML_ENCRYPTION_KEY=парольная-фраза-для-шифрования-моделей
python -m app
```

Сервис слушает `127.0.0.1:8001`. Чтобы разместить его на отдельном узле, задайте `ML_HOST=0.0.0.0`
и укажите адрес узла в настройке `forecast.ai.base-url` серверной части.

## Настройки (переменные окружения)

| Переменная | По умолчанию | Назначение |
|---|---|---|
| `ML_API_KEY` | `dev-ml-key-change-me` | общий секрет «сервер ↔ ML-сервис» (обязательно сменить) |
| `ML_ENCRYPTION_KEY` | — | парольная фраза: артефакты моделей шифруются AES-256-GCM |
| `ML_MODELS_DIR` | `models` | каталог реестра моделей |
| `ML_HOST`, `ML_PORT` | `127.0.0.1`, `8001` | адрес прослушивания |
| `ML_SSL_CERTFILE`, `ML_SSL_KEYFILE` | — | HTTPS между узлами (PEM) |
| `ML_MAX_CONCURRENT_TRAININGS` | `1` | число одновременных обучений |
| `ML_DOCS_ENABLED` | `true` | публиковать Swagger UI |

## Безопасность

* Все операции, кроме `/health`, требуют `X-API-Key`; сравнение ключа выполняется за постоянное время.
* Артефакты моделей — JSON (без `pickle`), при заданном ключе шифруются AES-256-GCM (ключ из парольной
  фразы через PBKDF2, 200 000 итераций); тег аутентификации выявляет подмену файла.
* Идентификатор модели проверяется по шаблону — выход за пределы каталога реестра невозможен.
* Входные данные строго валидируются (понедельники, отсутствие пропусков, неотрицательность, размеры).

валидация на синтетике с известными параметрами каналов. Отчёт воспроизводится командой
`python -m tools.validation_report docs\validation-report.md`.
